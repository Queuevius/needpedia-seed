BOTSKILL: FILE INTAKE

== PURPOSE ==

Freelancers and volunteers regularly deliver files: design assets,

video, documents, code-adjacent artifacts. This skill defines how to

receive them cleanly. Primarily for Adele.

== THE TWO ROUTES ==

1. NEXUS UPLOAD TILE (preferred for anything multi-file): the

community nexus (nexus.needpedia.org) has a drag-and-drop upload

tile for freelancers that PRESERVES FOLDER STRUCTURE, including

subfolders. It's password-gated: the volunteer requests access and

the password is provided through a private channel — direct email

to Needpedia@gmail.com — never through the

public inbox, and never by the AI. If someone posts the password

publicly by accident, flag it for the VC immediately so it can be

changed.

2. EMAIL ATTACHMENTS: fine for single files or small batches. Remember

which system is public: attachments sent through the public email

system are publicly visible — anything sensitive or unreleased goes

via private email instead.

== INTAKE CHECKLIST (walk the contributor through it) ==

- STRUCTURE: one top-level folder named for the task/project;

subfolders as needed; no loose files named "final_v2_REAL(3)".

- NAMING: descriptive-lowercase-with-dashes, dates as YYYY-MM-DD.

- FORMATS: prefer open/standard formats (PNG/SVG, PDF, MP4, plain

text/Markdown); include source files (PSD, AI, project files) in a

/source subfolder when they exist — future volunteers will need

them.

- A README.txt in the top folder: what this is, which task card it

fulfills, who made it, date, and any license/attribution notes for

third-party assets they used.

- RIGHTS: contributors should only submit work they made or have

rights to, and note any stock/third-party assets and their licenses.

- CONFIRM: after upload, the contributor posts in the public inbox

that the delivery is in (name the folder, not the password!) so the

work is on the record, credited, and findable.

== IF THINGS GO WRONG ==

Files too big, wrong format, upload fails → attachments in smaller

batches, or ask the VC in the public inbox for guidance. Never have

contributors put deliverables on random third-party file hosts without

VC approval — links rot and access gets lost.
