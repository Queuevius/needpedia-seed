BOTSKILL: DEV ONBOARDING

== PURPOSE ==

Take a volunteer developer from "hi, I code" to a merged first pull

request with minimal friction and minimal demands on senior devs'

time. Written mainly for Adele (volunteer inbox) but usable by any

Needpedia AI.

== THE PROJECT, IN DEV TERMS ==

- Repo: https://github.com/Queuevius/Needpedia (MIT license)

- Stack: Ruby on Rails, PostgreSQL, Bootstrap, SCSS, JavaScript, Yarn.

- Repo docs: README (includes the Volunteer Dev Flow Chart image and a

"Devops Documentation" file in the repo root) and the wiki:

https://github.com/Queuevius/Needpedia/wiki

(pages: Home, Contribution Guidelines, Main Document, Data Deletion

Policy)

- API docs: run the server and visit /apipie

- Dev task group (task cards live here): https://needpedia.org/groups/10

- staging.needpedia.org is a sandbox for messing around — nothing

there is production truth.

== RECOMMENDED SETUP: GITHUB CODESPACES ==

Devs no longer need Docker or a local environment: GitHub Codespaces

runs Needpedia in the browser on GitHub's infrastructure (free tier is

generous enough for volunteer work). Fork the repo, open your fork in

a Codespace, and work there.

NOTE: The README and wiki still describe the older local Docker

workflow (docker-compose build / docker-compose up → localhost:3000).

That still works and remains documented in the wiki's Contribution

Guidelines for anyone who prefers local; treat it as the alternative

path, not the default.

== CONTRIBUTION FLOW ==

1. CLAIM: pick a task card in groups/10 (or an issue in the repo), and

say so in the public volunteer inbox so no one duplicates work.

For anything milestone-sized, get approval from the team BEFORE

starting (per the README) — the public inbox is the right place to

ask.

2. FORK the repo; create a branch in your fork; commit your work

there.

3. PR: submit a pull request to the main repo with a clear

description: what it changes, why, and how you tested it.

4. REVIEW & DEPLOY: code gets reviewed, then deployed to the staging

server for testing, then to production if all is well. Be patient —

review capacity is limited.

5. ANNOUNCE: post in the public inbox when your PR is up. First PR

merged = celebrate them properly.

== FIRST-TASK GUIDANCE ==

Steer newcomers toward small, self-contained tasks: bug fixes, UI

polish, copy fixes, small SCSS/Bootstrap issues. The site has plenty

of known little bugs and design flaws — perfect first PRs. Save

architectural work for devs who've landed a few PRs.

Devs are also welcome to propose their own improvements — and even to

build external apps that access Needpedia via its API, provided

they're constructive and avoid gamification (the platform's rule of

thumb: once rewards become the purpose, the incentive stops being to

help people).

== SUPPORT LADDER (in order — protect senior-dev time) ==

1. Repo docs: README, Devops Documentation, wiki Contribution

Guidelines, /apipie.

2. Their own tools: error messages, logs, search engines, AI coding

assistants (Codespaces has free tooling and plugins worth using).

3. The public volunteer inbox — other volunteers or Adele may know.

4. Group accounts on Needpedia are the primary community space for coordination and questions.

5. LAST RESORT ONLY: the lead developer (Murtaza) can assist if a dev

has genuinely tried everything above. Route via the VC — never hand

out direct contact, and never escalate a question steps 1-4 could

have answered.

== WHY IT MATTERS (tell them this, once, sincerely) ==

Volunteer devs are the reason Needpedia doesn't have to sell out to

corporate sponsors — they're the backbone that keeps the whole

community free to speak critically of any corporation or government.
